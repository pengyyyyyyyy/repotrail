# 产品规格与验收

## 已确定的产品决策

| 决策 | 结果 |
| --- | --- |
| 首要目的 | AI 应用与 Agent 开发岗位的求职作品 |
| 首要场景 | 第一次阅读陌生仓库，找到入口、解释核心模块并追踪一条流程 |
| 开发基础 | Python 为主，轻量前端 |
| 首版投入 | 两周，每周约 10–15 小时 |
| 预算 | 自备云端模型 API，首版总计约 100–200 元 |
| 展示形式 | 本地网页与 Python CLI |
| 输入范围 | 公开的中小型 Python 仓库，GitHub URL 或本地克隆目录 |
| 技术主线 | 执行流程阅读与证据校验 |
| 未确认关系 | 有限补查，继续输出已有依据的部分并报告缺口 |
| 导览开始方式 | 系统推荐 1–3 条候选流程，用户点选 |
| 模型接口 | Chat Completions 兼容 API |
| 评测 | 三个 Python 仓库，约十五道源码核对题，同模型基础方案对照 |
| 对外语言 | 中英双语 README，默认中文导览 |
| 协作方式 | 先实现，由用户逐模块学习与复核 |

实现时暂用项目名 RepoTrail，采用 FastAPI、原生 HTML/CSS/JavaScript 和 MIT 许可证。这些属于本轮实现选择。

## 用户故事

作为第一次接触仓库的开发者，我希望先看到入口与核心模块，再选一条流程逐步读源码。每一步应说明读什么、对应哪些代码、与已读步骤有什么关系，以及还有哪些连接或解释需要核实。

## 正常流程

1. 输入仓库地址或目录，建立只读源码快照
2. 查看最多三条候选流程和按静态引用排序的模块地图
3. 选定流程，模型使用受限工具读取源码并输出结构化导览
4. 程序检查入口、符号、重复步骤与静态连接，必要时修订一次
5. 在网页中切换步骤、对照源码，导出 JSON、Markdown 或 CodeTour

## 可检查的验收条件

- 每个被定位的步骤来自当前快照，包含符号 ID、文件、起止行、原文与内容哈希
- 未知符号会计入缺口，请求步骤数与成功定位数同时显示
- 调用关系的来源步骤必须已读，连接依据保存调用文件与行号
- 静态匹配与未解决连接分别显示，说明文字保留人工复核状态
- 模型输出不合法、接口失败、未知仓库、超出输入上限均返回明确反馈
- 同一服务最多容纳两个生成任务，一个执行、一个等待
- 模型输出最多十二步，工具轮次与修订次数受限
- CLI 和网页共用索引、生成、校验与导出逻辑
- 固定评测记录源码版本、参考问题、模型配置、调用统计与原始导览

## 首版边界

最多 300 个 Python 文件、单文件 200 KB、总计 4 MB。索引会跳过无法解析的文件并记录警告。源码快照在一次分析中保持不变，重新打开本地目录会重新读取。远程缓存保留首次克隆版本。

输入仓库的代码只作解析和阅读材料。源码上下文在用户发起模型生成时发送到其配置的服务。前端在生成前显示该行为，API Key 从服务端环境变量读取。

## 验证状态

离线示例、真实仓库索引、网页操作、导出与自动化测试已完成首轮验证。三个锁定版本仓库的十五个参考符号与源码片段已通过脚本核验。

真实模型对照、参考答案的独立人工复核、解释语义评分、使用者任务耗时实验待完成。预算是否足够需要依据实际模型价格与调用记录判断。

## 后续两周的复核安排

第一阶段逐模块阅读 index.py、engine.py 与测试，确认自己能解释符号解析和静态证据边界。第二阶段配置 API、运行固定对照并完成语义评分。第三阶段根据实际失败案例修正入口推荐或上下文选择，再将实测数据补入 README 与简历。
